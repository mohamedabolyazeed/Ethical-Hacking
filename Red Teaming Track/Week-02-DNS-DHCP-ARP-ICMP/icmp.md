# ICMP — فهم البروتوكول وتطبيقاته

**المسار:** Red Teaming Track  
**الأسبوع:** Week 02 — DNS, DHCP, ARP & ICMP  
**التاسك:** فهم ICMP واستخداماته

## 1. ما هو ICMP؟

**ICMP** اختصار **Internet Control Message Protocol**. يُستخدم للتشخيص والإبلاغ عن بعض أخطاء الاتصال، ويعمل مع IP في **طبقة الشبكة — Layer 3**.

على سبيل المثال، قد يُبلغ المرسل بأن الوجهة غير قابلة للوصول، أو بأن قيمة TTL انتهت أثناء مرور الحزمة عبر الشبكة.

- لا يستخدم منافذ TCP أو UDP؛ البروتوكول له رقم مستقل داخل IPv4 وهو **1**.
- يستخدم **Type** لتحديد نوع الرسالة و**Code** لتحديد سببها بالتفصيل.
- ليس بروتوكول نقل لبيانات التطبيقات مثل HTTP، لكن رسائل Echo يمكن أن تحمل بيانات اختبار تُعاد في الرد.

> أرقام Type وCode المذكورة هنا تخص **ICMPv4**. يستخدم IPv6 بروتوكول **ICMPv6**، وله أرقام رسائل مختلفة.

## 2. أهم أنواع الرسائل

| الرسالة | Type في ICMPv4 | الاستخدام |
| --- | --- | --- |
| Echo Request | 8 | طلب رد من الهدف؛ يستخدمه `ping` |
| Echo Reply | 0 | الرد على طلب Echo Request |
| Destination Unreachable | 3 | الإبلاغ عن تعذر الوصول، مع Code يوضح السبب |
| Time Exceeded | 11 | الإبلاغ عن انتهاء TTL، أو انتهاء مهلة إعادة تجميع الأجزاء |
| Redirect | 5 | اقتراح بوابة أخرى لبعض حركة المرور؛ موضوع إضافي |

### Echo Request وEcho Reply

عند تشغيل `ping`، يرسل جهازك **Echo Request**. إذا استقبل الهدف الطلب وسمحت إعداداته ومسار الشبكة بالرد، يعيد **Echo Reply**.

يمكن استخدام النتيجة لملاحظة:

- وصول الرد من الهدف أثناء الاختبار.
- زمن الذهاب والعودة **RTT**.
- عدد الطلبات التي لم يصل لها رد خلال المهلة.

**نجاح Ping لا يثبت أن موقع الويب أو أي خدمة أخرى تعمل.** فقد يرد الجهاز على ICMP بينما تكون خدمة HTTPS متوقفة.

### Destination Unreachable

رسالة Type 3 لها عدة Codes، منها:

| Code | الاسم | معنى الرسالة |
| --- | --- | --- |
| 0 | Network Unreachable | تعذر الوصول إلى شبكة الوجهة |
| 1 | Host Unreachable | تعذر الوصول إلى الجهاز الهدف |
| 2 | Protocol Unreachable | بروتوكول IP المطلوب غير مدعوم عند الهدف |
| 3 | Port Unreachable | المنفذ غير متاح؛ يظهر عادةً مع UDP، وليس الرد المعتاد لمنفذ TCP مغلق |
| 4 | Fragmentation Needed | الحزمة أكبر من MTU للوصلة التالية، وعلامة DF تمنع تجزئتها |

> الرسالة تساعد على التشخيص، لكنها لا تكفي وحدها لتحديد السبب الجذري للعطل. راجع مصدر الرسالة والـCode وبقية الاختبارات.

### Time Exceeded وTTL

في IPv4، تحتوي الحزمة على قيمة **TTL**. يقلل كل راوتر يوجّه الحزمة هذه القيمة. إذا انتهت أثناء التوجيه، يتخلص الراوتر من الحزمة، ويمكن أن يرسل **Time Exceeded — Type 11, Code 0** إلى المصدر.

هذه الآلية تمنع الحزم من الدوران إلى أجل غير محدد إذا حدث Routing Loop.

**Code 1** من نفس النوع يتعلق بانتهاء مهلة إعادة تجميع أجزاء حزمة IP، وليس بانتهاء TTL أثناء التوجيه.

## 3. كيف يعمل tracert؟

يستخدم أمر Windows `tracert` طلبات ICMP Echo بقيم TTL متزايدة:

1. **TTL = 1:** تنتهي القيمة عند أول راوتر، وقد يرد برسالة Time Exceeded.
2. **TTL = 2:** يمكن أن تصل الحزمة إلى الراوتر الثاني قبل انتهاء القيمة.
3. يكرر الأمر التجربة بقيم أعلى حتى يرد الهدف أو يصل إلى الحد الأقصى.

| ما يظهر في النتيجة | تفسيره |
| --- | --- |
| رقم Hop | موضع القفزة في الاختبار |
| ثلاث قيم بالـms | أزمنة ذهاب وعودة لثلاث محاولات من جهازك إلى تلك النقطة |
| عنوان IP أو اسم | الجهاز الذي أرسل الرد |
| `*` | لم يصل رد على المحاولة خلال المهلة |

- الأزمنة ليست زمن الانتقال بين راوترين متجاورين.
- آخر قفزة قد تكون الجهاز الهدف؛ ليست كل القفزات راوترات.
- النجوم لا تثبت أن الراوتر متوقف أو أن المرور توقف عنده.
- على Linux، قد يستخدم `traceroute` افتراضيًا UDP؛ طريقة الاختبار تختلف باختلاف الأداة وخياراتها.

## 4. التطبيق العملي — نتائج جهازي

النتائج التالية من التطبيق الفعلي المرفق، وليست نتائج افتراضية. العناوين وأزمنة الاستجابة قد تختلف عند تكرار التجربة.

### التجربة الأولى: Ping

**الأمر:**

```powershell
ping -n 4 google.com
```

**النتيجة:**

```text
Pinging google.com [142.251.209.78] with 32 bytes of data:
Reply from 142.251.209.78: bytes=32 time=323ms TTL=117
Reply from 142.251.209.78: bytes=32 time=589ms TTL=117
Reply from 142.251.209.78: bytes=32 time=828ms TTL=117
Reply from 142.251.209.78: bytes=32 time=1327ms TTL=117

Ping statistics for 142.251.209.78:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),
Approximate round trip times in milli-seconds:
    Minimum = 323ms, Maximum = 1327ms, Average = 766ms
```

**تحليل النتيجة:**

| القيمة | ما تعنيه |
| --- | --- |
| Sent = 4 / Received = 4 | وصلت ردود على الطلبات الأربعة أثناء الاختبار |
| Lost = 0 | لم يُلاحظ فقد في الأربع محاولات؛ لا يثبت غياب الفقد طوال الوقت |
| RTT = 323–1327 ms | زمن الذهاب والعودة مرتفع ومتغير في هذه العينة |
| Average = 766 ms | متوسط زمن الذهاب والعودة للمحاولات الأربع |
| TTL = 117 | قيمة TTL المتبقية في الرد عند وصوله إلى جهازي |

**الاستنتاج:** استجاب الهدف للاختبار، لكن التأخير مرتفع ومتغير. لا يمكن تحديد سببه من أربع محاولات فقط.

**ملاحظة TTL:** لا يمكن حساب عدد الراوترات بدقة من `TTL = 117` دون معرفة قيمة TTL الأصلية للرد. كما أن مسار الرد قد يختلف عن مسار الطلب.

### التجربة الثانية: Tracert

**الأمر:**

```powershell
tracert google.com
```

**النتيجة:**

```text
Tracing route to google.com [142.251.209.78]
over a maximum of 30 hops:

  1     5 ms    14 ms     5 ms  192.168.1.1
  2    36 ms    37 ms    27 ms  100.89.0.1
  3    32 ms    30 ms    35 ms  10.38.83.229
  4     *        *        *     Request timed out.
  5     *        *        *     Request timed out.
  6     *        *        *     Request timed out.
  7     *        *        *     Request timed out.
  8     *        *        *     Request timed out.
  9     *        *        *     Request timed out.
 10    75 ms    79 ms    73 ms  ncmrsa-ai-in-f14.1e100.net [142.251.209.78]

Trace complete.
```

**تحليل النتيجة:**

| القفزة | الملاحظة | التفسير |
| --- | --- | --- |
| 1 | رد من `192.168.1.1` | أول نقطة ردّت؛ تتوافق مع الراوتر المحلي في هذه التجربة |
| 2 | رد من `100.89.0.1` | نقطة تالية في المسار؛ العنوان وحده لا يحدد وظيفة الجهاز بدقة |
| 3 | رد من `10.38.83.229` | نقطة أخرى ردّت في المسار |
| 4–9 | لم تصل ردود خلال المهلة | قد يكون السبب فلترة أو تحديد معدل الردود أو فقد حزم؛ السبب غير محسوم |
| 10 | رد من عنوان الهدف | وصل الاختبار إلى الهدف عند Hop 10، بزمن ذهاب وعودة 73–79 ms |

**الاستنتاج:** استلمنا ردودًا من القفزات **1 و2 و3 و10**. غياب الردود من القفزات 4–9 لم يمنع وصول الاختبار إلى الهدف.

**مقارنة مع Ping:** كان زمن الاستجابة للهدف في Tracert أقل من تجربة Ping. الاختباران حدثا في أوقات مختلفة؛ لا تكفي هذه النتائج وحدها لنسب التأخير إلى راوتر بعينه.

## 5. لماذا فشل Ping لا يثبت توقف الجهاز؟

عند ظهور `Request timed out`، فالنتيجة المؤكدة هي: **لم يصل Echo Reply خلال المهلة**.

الأسباب المحتملة تشمل:

- حظر طلبات Echo أو ردودها بواسطة Firewall.
- تحديد معدل رسائل ICMP.
- فقد حزم أو ازدحام أو تأخير كبير.
- مشكلة في مسار الذهاب أو العودة.
- تعطل الجهاز أو الاتصال؛ وهو احتمال يحتاج فحصًا مع باقي الاحتمالات.

### اختبارات مساعدة على Windows

نفّذ كل أمر منفصلًا، وسجّل نتيجته قبل الاستنتاج:

| الاختبار | الأمر | ما يساعد على فحصه |
| --- | --- | --- |
| Loopback | `ping 127.0.0.1` | استجابة مكدس IP المحلي؛ لا يختبر الكابل أو الراوتر |
| البوابة المحلية | `ping <Default-Gateway>` | استجابة البوابة عبر الاتصال المحلي، إذا كانت تسمح بـEcho |
| عنوان خارجي | `ping 1.1.1.1` | استجابة هدف خارجي دون الاعتماد على DNS لحل اسمه |
| DNS | `nslookup google.com` | إمكانية حل اسم النطاق بواسطة خادم DNS المستخدم |
| مسار الاتصال | `tracert -d 1.1.1.1` | القفزات التي ترد، دون تحويل عناوينها إلى أسماء |
| اتصال TCP | `Test-NetConnection google.com -Port 443` | إمكانية إنشاء اتصال TCP على المنفذ 443؛ لا يثبت نجاح TLS أو HTTP |

> استبدل `<Default-Gateway>` بعنوان البوابة الموجود في إعدادات جهازك. هذه اختبارات مقترحة؛ ليست كلها تجارب موثقة في هذا الملف.

## 6. قراءة إضافية: ICMP Redirect

قد يرسل راوتر **ICMP Redirect — Type 5** ليقترح على المضيف استخدام بوابة أخرى للوصول إلى وجهة معينة، في ظروف محددة داخل الشبكة المحلية.

- الرسالة اقتراح للمضيف، وليست تغييرًا مضمونًا لمساره.
- قبولها يعتمد على إعدادات النظام والتحقق من الرسالة.
- تفاصيل Cisco Nexus والتكوينات الخاصة به خارج نطاق تاسك الأساسيات الحالي.
